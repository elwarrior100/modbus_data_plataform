Capítulo 1 · Parte I

O mapa da plataforma

Objetivo: conseguir desenhar de memória as peças da plataforma, onde corre cada uma e por onde passa uma alteração de código até chegar a produção.

Uma plataforma de dados é o conjunto de serviços partilhados sobre os quais os projetos de dados correm: um orquestrador (Airflow), armazenamento (SeaweedFS e lakeFS), uma base de dados (Postgres), um catálogo (OpenMetadata), e a maquinaria para instalar, atualizar e proteger tudo isto. Um projeto (o Modbus) só traz o seu código, os seus DAGs e as suas imagens.

A plataforma corre em dois clusters iguais:

  • Local: uma VM Lima com k3s no teu Mac (8 CPU, 16 GB). Serve para desenvolver e experimentar. Desliga-se com o Mac.
  • Oracle: uma VM Always Free (Ampere A1, 2 OCPU, 12 GB, arm64) com k3s. É o ambiente sempre ligado, onde a recolha corre 24 horas por dia.

Os princípios que guiam tudo

  • Git é a fonte da verdade. O que corre num cluster é o que está no repositório platform. Alterar à mão no cluster é temporário: o Argo CD repõe o que diz o git.
  • Nenhum segredo no git. Nem cifrado. Os segredos vivem num cofre e são lidos pelo cluster.
  • Nenhuma porta aberta à internet. O acesso é por uma rede privada (Tailscale).
  • Imagens imutáveis. Cada imagem tem como tag o SHA do commit que a produziu: sabes sempre que código está a correr.
  • Custo zero e orçamento medido. Tudo cabe no Always Free da Oracle e nos planos grátis do GitHub e do Tailscale; os números de memória e CPU foram medidos, não estimados.

Capítulo 2 · Parte I

Kubernetes e k3s

Objetivo: perceber os objetos do Kubernetes que usamos, porque escolhemos o k3s, e porque é que parar uma VM com k3s pode corromper dados.

O Kubernetes é um sistema que mantém programas a correr segundo uma descrição: tu dizes "quero isto", ele faz com que seja verdade e volta a fazê-lo sempre que algo falha. O k3s é uma distribuição pequena do Kubernetes, num só binário, pensada para uma máquina só. É o que usamos nos dois clusters (v1.36.5+k3s1).

Os objetos que aparecem nesta plataforma

ObjetoO que éExemplo nosso

Deployment"Mantém N pods iguais a correr". Substitui os que falham.collector, writer, lakefs

Como o disco funciona aqui

O k3s traz o local-path-provisioner: cada PVC vira uma pasta no disco da própria VM (/var/lib/rancher/k3s/storage/…). É simples e grátis, mas tem duas consequências que importam: os dados vivem no disco da VM (se o disco se perde, perdem-se), e o tamanho pedido não é imposto (um PVC de 20 Gi pode crescer além disso).

Parar uma VM com k3s: o problema do KillMode

O serviço do k3s corre com KillMode=process: quando o sistema desliga, o systemd para o processo do k3s mas não pede aos contentores que terminem com calma. O Postgres e o SeaweedFS são mortos a meio de escrever. Foi exatamente isso que corrompeu o último commit do lakeFS duas vezes no Mac.

A solução no Mac foi o scripts/vm-stop.sh: primeiro um kubectl drain (pede a cada pod que termine, com SIGTERM e 60 s de tolerância), depois sync, e só então para a VM.

Resolvido na Oracle (capítulo 13b): o kubelet tem graceful node shutdown de 90 s (no ficheiro kubelet.conf.d, porque o Kubernetes 1.36 já não aceita a opção na linha de comando), provado com um reinício real.

O kernel que partia os sinais

No Mac, a VM atualizou-se sozinha para o kernel 7.0.0-42, em que o perfil AppArmor dos contentores recusava sinais entre processos do mesmo contentor. O Postgres não conseguia pedir um checkpoint, e o gosu ficava preso. A solução foi fixar o kernel 7.0.0-38. Na Oracle (kernel 7.0.0-1013-oracle) testou-se antes de avançar: um pod enviou SIGTERM a um processo filho e recebeu o código 143 (sinal entregue).

Onde estão os ficheiros

  • platform/envs/local/lima/industrial.yaml: a VM do Mac.
  • platform/envs/oracle/bootstrap-vm.sh: swap de 4 GB, sysctls e k3s fixo na mesma versão, com o nome Tailscale no certificado da API.
  • platform/scripts/vm-start.sh e vm-stop.sh: ligar e desligar o Mac com segurança.

Capítulo 3 · Parte I

Plataforma e projetos: dois tipos de repositório

Objetivo: explicar porque separámos o repositório em dois e porque não em mais (ADR-010).

No início estava tudo num repositório. Funcionava, mas misturava duas coisas que mudam por razões diferentes: o código (muda quando se programa) e a configuração dos ambientes (muda quando se decide o que corre e onde). E não servia para um segundo projeto.

platform (público)

Terraform, plataforma partilhada, lista de projetos, ajustes por ambiente. Muda quando muda a configuração ou a versão de uma imagem.

terraform/oracle/
platform/  argocd/ airflow/ k8s/ openmetadata/
projects/modbus/k8s/  ingest/ ot/
envs/local/  envs/oracle/
scripts/

um por projeto

Código, DAGs, Dockerfiles, testes, docs e o CI que publica imagens. Muda quando se programa.

ot/  ingest/  pipelines/
quality/  docs/  tests/
.github/workflows/ci.yml

Porque não um repositório por componente

O simulador, o ingest e a silver partilham contratos (o envelope dos eventos, o catálogo de tags, o formato do bronze) e os testes atravessam-nos (a semana sintética usa os três). Separados, cada mudança de contrato exigiria versões coordenadas entre repositórios. Para uma pessoa, é custo sem ganho.

Como foi feito sem perder a história

  1. git subtree split --prefix=platform criou um branch só com a história da pasta platform/ (16 commits).
  2. Esse branch foi clonado para /Users/mac/platform e reorganizado (git mv), para o git seguir os ficheiros.
  3. gitleaks correu sobre toda a história antes de a tornar pública: 0 fugas.
  4. O Argo CD foi reapontado para o repositório novo, e só depois se apagou platform/ do projeto.

Capítulo 4 · Parte I

GitOps com Argo CD

Objetivo: perceber o ciclo de reconciliação, a estrutura app-of-apps com uma raiz por ambiente, o ApplicationSet, e as regras de prune e selfHeal.

GitOps quer dizer que o estado desejado do cluster está no git, e um agente dentro do cluster (o Argo CD) compara continuamente o git com o que está a correr e corrige as diferenças. Ninguém faz kubectl apply à mão para mudanças duradouras.

A árvore de aplicações

  • Raiz por ambiente (envs/local/root-app.yaml, envs/oracle/root-app.yaml): uma Application com duas fontes: as aplicações partilhadas (platform/argocd/apps) e as do ambiente (envs/<env>/apps). Aplica-se uma vez por cluster, com kubectl apply.
  • Aplicações partilhadas: namespaces, data (Postgres, SeaweedFS, lakeFS), external-secrets (chart Helm), secrets (os ExternalSecrets da plataforma) e o ApplicationSet projects.
  • Aplicações do ambiente: secret-store, que é diferente em cada cluster (capítulo 5).
  • ApplicationSet projects: um gerador que cria uma aplicação por pasta projects/*/k8s/*. Hoje gera ingest e ot.

Prune, selfHeal e sync waves

OpçãoO que fazOnde a desligámos e porquê
selfHealRepõe o git se o cluster for mudado à mão.Ligado em todas.
pruneApaga do cluster o que deixou de estar no git.Desligado em data, namespaces, secrets e nos projetos: um ficheiro mudado de sítio não pode apagar uma base de dados ou o spool.
sync-waveOrdem de aplicação dentro da raiz.0: ESO; 1: data, secrets, secret-store; 2: projetos.

A mudança de repositório, feita sem apagar nada

Quando o Argo CD passou a ler o repositório novo, havia um risco: a raiz tinha prune: true, e as aplicações ot e ingest iam deixar de estar na pasta dela (passavam a vir do ApplicationSet). Fez-se em dois tempos: primeiro a raiz foi reapontada com o prune desligado; depois de confirmar que o ApplicationSet era o dono das duas, tirou-se a etiqueta de seguimento antiga e voltou a ligar-se o prune. Antes de tudo, kubectl diff mostrou que os manifests novos eram iguais ao que corria.

Descoberta pelo caminho: o Argo CD estava a ler um main antigo do projeto (o trabalho estava no branch test) e o ingest nem sequer era gerido por ele. Lição: confirma sempre que repositório e que branch cada aplicação lê (kubectl -n argocd get applications).
Agora sim, GitOps: o Airflow, o OpenMetadata e o próprio Argo CD passaram a aplicações Helm do Argo CD (valores no git). E a Oracle segue o branch oracle: uma mudança só lá chega quando promovida com promote-oracle.sh (ADR-012).

Capítulo 5 · Parte II

Segredos num cofre

Objetivo: explicar como uma palavra-passe vai do cofre até ao pod sem nunca passar pelo git, e o problema do "segredo zero" (ADR-011).

As palavras-passe (Postgres, SeaweedFS, lakeFS, Airflow, OpenMetadata) vivem no OCI Vault, o equivalente da Oracle ao Azure Key Vault. Cada cluster tem o External Secrets Operator (ESO), que lê o cofre e cria os Secrets do Kubernetes. No git só existe a referência: "o Secret postgres-auth vem do segredo data-postgres-auth do cofre".

As peças, uma a uma

  • O cofre (terraform/oracle/vault.tf): tipo DEFAULT (grátis; o VIRTUAL_PRIVATE é pago), chave mestra AES-256 protegida por software (grátis), num compartment próprio platform-secrets.
  • Um segredo do cofre por Secret do Kubernetes, com todas as chaves em JSON. Nome: <namespace>-<secret>. O ESO reconstrói o Secret com um só dataFrom.extract.
  • Segredos derivados: o lakefs-credentials (em ingest e airflow) não é guardado: o ESO constrói-o a partir de data-lakefs-auth. Uma só fonte da verdade.
  • ClusterSecretStore oci-vault: diz ao ESO onde está o cofre e como se autenticar. É o único objeto diferente entre ambientes.

O segredo zero

Para ler o cofre, o ESO precisa de provar quem é. Essa prova é o "segredo zero": o único que não pode vir do cofre.

  • No Mac: a chave API de um utilizador só de leitura, eso-reader. A chave privada foi gerada no Mac e só a pública foi dada à Oracle. O script eso-local-key.sh põe-na num Secret do cluster, sem a mostrar.
  • Na Oracle: instance principal. Um grupo dinâmico diz "esta VM pode ler segredos de platform-secrets". A VM prova quem é ao serviço de metadados da Oracle: não há nenhuma chave guardada no cluster.

Como se encheu o cofre sem quebrar nada

  1. vault-seed.sh leu os 11 Secrets que existiam no cluster local e copiou os valores para o cofre (gerar valores novos partiria as bases de dados). O pedido à Oracle vai num ficheiro temporário com permissão 600, nunca como argumento.
  2. Verificação: o hash SHA-256 de cada segredo no cofre é igual ao do cluster (11 de 11).
  3. Um ExternalSecret de teste leu data-postgres-auth para um Secret à parte: mesmo hash.
  4. Os 13 ExternalSecrets reais foram aplicados: o ESO adotou os Secrets existentes com os mesmos valores. Nenhum pod reiniciou.
Erro corrigido: eu tinha escrito que deletionPolicy: Retain mantinha o Secret se o ExternalSecret fosse apagado. Não é verdade: isso depende do creationPolicy. Com Owner, o Secret seria apagado com ele; agora é Orphan, e nenhum Secret tem dono.
Risco fechado: o instance principal autoriza a VM inteira, por isso há uma NetworkPolicy que bloqueia 169.254.169.254 em todos os namespaces de trabalho. Só external-secrets e backup o alcançam, e a exceção é o namespace (não uma etiqueta que um pod pudesse pôr).

Capítulo 6 · Parte II

Rede sem portas abertas

Objetivo: perceber como acedes à Oracle sem nenhuma porta aberta à internet, e as alternativas aos túneis.

A VM da Oracle tem uma firewall (a security list da subnet) sem nenhuma regra de entrada exceto ICMP para o tamanho dos pacotes. Nem a porta 22 do SSH. Como se entra?

Pelo Tailscale: uma rede privada (VPN em malha) entre o Mac e a VM. O Tailscale só precisa de tráfego de saída: os dois lados ligam-se a um coordenador e encontram-se, diretamente ou por um relay (DERP) quando não conseguem. No nosso caso passa pelo relay de Madrid, cifrado de ponta a ponta, a ~30 ms.

Como foi feito, com a ordem que evita ficares trancado

  1. Instalar o Tailscale na VM (repositório oficial de pacotes) e no Mac; entrar com a mesma conta.
  2. Testar ssh ubuntu@platform-oracle pelo Tailscale antes de mexer na firewall.
  3. Desativar o "key expiry" da VM na consola do Tailscale, para ela não sair da rede ao fim de 6 meses.
  4. Só então fechar a porta 22, por Terraform (network.tf). Depois: SSH pelo IP público dá timeout; pelo Tailscale entra.
  5. Plano B se o Tailscale falhar: a consola de série da Oracle, que não usa a porta 22.

Ver os serviços: túneis ou Ingress

  • Túneis (scripts/ui.sh): kubectl port-forward para cada serviço. Simples, mas só vivem enquanto o script corre.
  • Ingress com o Traefik que o k3s já traz: regras "quem pedir airflow.localhost vai para o Airflow". Sempre disponível e declarado no git. No Mac já respondia na porta 80.
  • Na Oracle, o Ingress só deve escutar na rede do Tailscale, nunca na pública.

Como usar: abrir os serviços no browser

O import: adotar sem recriar

A VM agente-01 e a firewall foram criadas na consola, por isso o Terraform não as conhecia: um apply tentaria criar outra VM (e o Always Free só tem lugar para uma). A solução foi um bloco import:

import {
  to = oci_core_instance.platform
  id = var.instance_ocid        # vem do terraform.tfvars, fora do git
}

A regra de ouro: antes do apply, o plan tem de dizer "1 to import, 0 to add, 0 to change, 0 to destroy". Para isso, os valores no tfvars foram copiados da VM real (nome, disco de 47 GB, a mesma chave SSH). Com o disco por omissão de 100 GB, o plan queria alterar a VM.

Proteções escritas no código

  • ignore_changes = [source_details[0].source_id]: uma imagem Ubuntu mais nova não força a recriação da VM.

Objetivo: perceber o que faz o CI, porque corre em arm64, e como uma imagem nova chega aos clusters.

Capítulo 9 · Parte IV

Airflow como plataforma

Objetivo: perceber como um Airflow partilhado corre DAGs de vários projetos, cada um com a sua imagem.

O Airflow corre com o KubernetesExecutor: cada tarefa nasce num pod novo e morre no fim, por isso só gasta memória enquanto trabalha. A plataforma usa a imagem oficial apache/airflow:3.2.2, sem código de nenhum projeto lá dentro.

As três ideias

  1. DAG bundles. dag_bundle_config_list lista um bundle por projeto (GitDagBundle: repositório, branch, pasta, intervalo). O provider de git já vem na imagem oficial. Um DAG novo aparece no Airflow sem imagem nova.
  2. Imagem por tarefa. O DAG lê MODBUS_PIPELINES_IMAGE e passa-a em executor_config={"pod_override": …}. Cada projeto traz as suas dependências sem colidir com os outros.
  3. Em série. parallelism = 2 no Airflow inteiro e max_active_runs = 1 no DAG. Medido: 1 180 horas em 137 s com um worker; uma hora normal demora ~1 s.

A prova, com output real

No Mac, um run manual da silver: o pod usou ghcr.io/elwarrior100/modbus-pipelines:44008786…, clonou o DAG desse commit ("Cloning repository… version 44008786…") e o G2 recusou a hora 12 com razão (34 de 60 minutos com dados, porque a VM só arrancou às 12:27).

Deriva fechada: o tracking_ref do bundle é o mesmo SHA da imagem das tarefas, e os dois mudam no mesmo commit do repositório platform.

Precisas de uma imagem nova (o CI publica-a com o SHA novo) e de mudar MODBUS_PIPELINES_IMAGE no platform, que hoje ainda obriga a correr o install-airflow.sh em cada cluster.
Ver resposta

Auditoria de custos (16-11): "custo zero" não é o mesmo que "barato"

  • O ponto de partida: a conta da Oracle é pay-as-you-go. Se algo passar os limites grátis, a Oracle cobra; não bloqueia. Um agente independente concluiu "custo zero: NÃO" e apontou porquê:
    • a spool do Postgres crescia sem fim (~370 MB por dia);
    • a cópia do lake podia chegar a ~7 vezes o tamanho do lake;
    • não havia nada que parasse um gasto, só avisos.
  • Corrigido (grátis):
    • a spool guarda 7 dias de lotes exportados e 30 de rejeitados (CronJob spool-retention);
    • a cópia do lake faz um pacote completo por semana, e o próprio Object Storage apaga pacotes e catálogos com mais de 9 dias (~2,5 vezes o lake, em vez de ~7);
    • há um alarme para o total do Object Storage acima de 15 GB;
    • os envios a meio são abortados ao fim de 2 dias.
  • A fatura de novembro: €0,0198. A limpeza da cópia antiga, objeto a objeto (~20 mil pedidos de "apagar"), fez passar o limite grátis do mês. Lição: apagar muitos objetos faz-se com uma regra de ciclo de vida do bucket (grátis), não com um pedido por objeto.

O corta-custos (ADR-017): parar sozinho, nunca apagar

  • O que faz: um CronJob de hora a hora (ops/cost-guard) lê o gasto do mês na API de orçamentos. Se chegar a €1,00:
    1. cria uma quota que põe a zero 48 famílias de serviços pagos, para que nada pago se possa criar;
    2. desliga a própria VM com um encerramento ordenado (SOFTSTOP), para que nenhum job faça pedidos;
    3. nunca apaga dados.
    A retoma faz-se do Mac, com scripts/cost-guard-resume.sh.
  • Porque não uma Oracle Function, como o Gemini sugeria: precisava de uma imagem no registo da Oracle e de um token para a enviar, mais uma peça para manter. O CronJob usa o que já existe: a identidade da VM e as regras de rede.
  • Privilégio mínimo: a VM pode criar quotas mas não as apagar nem alterar. Uma VM comprometida não consegue levantar a quota que a parou.
  • Provado a sério: com o limite baixado a €0,001, o guarda criou a quota e a VM ficou parada em ~1,5 min. O script de retoma religou-a e as 19 aplicações voltaram Healthy em ~10 min, sem dados perdidos.
  • Os detalhes que o teste e as revisões apanharam:
    • Desarme por engano: o script de retoma desarmava o guarda até ao fim do mês, mesmo num teste. Agora só põe a etiqueta se o gasto passar mesmo €1.
    • Mês retomado sem teto: um mês retomado ficava sem limite nenhum. Agora o limite é o gasto no momento da retoma mais €1.
    • Viragem do mês: os dados do orçamento chegam atrasados e, no dia 1, ainda podem trazer o gasto do mês anterior. O guarda ignora um gasto calculado antes do mês atual.
    • Números estranhos: um gasto minúsculo pode aparecer como 3.4e-07; agora é lido corretamente.
    • Prazo para religar: com a VM parada, a regra dos 9 dias continua a apagar pacotes. Por isso, religar em menos de 9 dias.

Incidente de 17-11: o que funciona pequeno parte quando cresce

  • O que se viu: três emails de manhã. A cópia do lake falhou, o ensaio de restauro falhou e o alarme de pedidos continuava a disparar. O gasto não mudou (€0,0198).
  • Causa 1, o envio em partes. O pacote da noite (9440 objetos novos) passou os 256 MB a partir dos quais o rclone envia em várias partes (multipart). Na Oracle, começar um envio em partes exige a permissão OBJECT_OVERWRITE. A VM não a tem, de propósito, porque é isso que torna a cópia impossível de adulterar. A resposta da Oracle a uma permissão em falta foi "404 BucketNotFound": enganadora, mas é assim que ela esconde o que não podes ver. Correção: enviar sempre num só pedido (até 5 GiB no rclone). O backup do Postgres tinha o mesmo risco a dias de distância (dump da spool com 107 MB, para um limite de 128 MiB) e ficou com --no-multipart.
  • Causa 2, o ensaio tinha um SeaweedFS temporário pequeno demais: 20 volumes de 64 MB. Com o lake a passar 1 GB, deixou de ter onde escrever. Correção: volumes de 256 MB, tantos quanto o disco temporário permitir.
  • A causa de fundo, os índices do lakeFS. O lake tinha 1,0 GB, dos quais 82% eram índices (_lakefs/) e só 18% eram dados. A cada commit o lakeFS guarda a lista de todos os ficheiros, partida em pedaços ("ranges"). Por omissão um pedaço leva 50 000 ficheiros, por isso o lake inteiro cabia num só pedaço de ~0,5 MB, reescrito em cada commit: 2 por minuto, ~2900 por dia. E a GC nunca apaga commits, logo estes índices nunca seriam limpos. Correção: pedaços de ~1000 ficheiros (range_raggedness_entries), para cada commit reescrever só o último pedacinho.
  • Também: a CPU reservada estava a 97% (usada: ~20%) e os jobs ficavam à espera de vaga. As reservas dos serviços parados baixaram para o uso medido com folga: 79%.
  • A lição: um teste que passa hoje só prova o tamanho de hoje. Cada limite (de envio, de volume, de partição, de reserva) tem de ser comparado com a velocidade a que o dado cresce, e com a data em que lá chega. Foi por isso que se pediu a seguir uma auditoria de "bombas-relógio".

Monitorização e alarmes

Objetivo: perceber porque há duas camadas de alertas, uma dentro e outra fora da VM.

Dentro do cluster: Prometheus + Grafana

kube-prometheus-stack pelo Argo CD. Métricas de todos os pods, 24 dashboards de Kubernetes, regras de alerta visíveis no Grafana. ~930 Mi na Oracle. Abre-se em localhost:3000 (ui.sh); palavra-passe no cofre.

Fora da VM: alarmes da Oracle

OCI Monitoring + Notifications (grátis), por email: VM sem métricas há 10 min, CPU > 90 % durante 30 min, memória > 92 % durante 15 min, e nenhum backup bem-sucedido em 24 h (o job publica backup_success). Hoje são 20 alarmes. Os "sinais de vida" de cada job: backup, cópia do lake, ensaio de restauro, GC, frescura da silver, disco e corta-custos. Os limites de custo: pedidos por dia, espaço por bucket e no total, e gasto do mês. Mais um que conta os alertas do Prometheus a disparar.

Alertas do Prometheus sem Alertmanager: as 220 regras do Prometheus mostravam alertas no Grafana, mas ninguém os recebia. O job ops/node-health conta, de 30 em 30 min, os alertas warning e critical a disparar (exceto o Watchdog, que dispara sempre de propósito) e envia o número à Oracle. Acima de 0, chega um email. Formatos e particionamento

  • Parquet é colunar: guarda cada coluna junta, comprimida, em row groups com estatísticas (min/max). Quem lê só uma coluna, ou filtra por valor, salta o resto (predicate pushdown). Por isso o DuckDB lê uma hora em milissegundos.
  • Particionar é dividir em pastas (dt=…/hour=…) para ler só o que interessa. Demasiadas partições pequenas é tão mau como poucas grandes (o problema dos "small files").
  • Formatos de tabela (Iceberg, Delta) juntam ao Parquet transações, versões e evolução de esquema dentro dos metadados da tabela. Aqui o lakeFS dá versões ao repositório inteiro; numa equipa maior, Iceberg é o padrão a conhecer.

Modelação para o gold (o próximo passo)

  • Modelo dimensional (Kimball): tabelas de factos (medições, eventos) e de dimensões (ativo, tag, tempo).
  • SCD tipo 2: guardar a história de uma dimensão (o PUMP-01 mudou de linha de produção em março) com valid_from/valid_to.
  • Agregados: médias horárias, OEE, tempos de paragem. São o produto que os dashboards e o ML consomem.

Contratos de dados

Um contrato é um acordo escrito entre quem produz e quem consome: esquema, significado, limites, frescura esperada e o que acontece quando falha. Aqui: docs/silver-contract.md e docs/gates-contract.md. O gate transforma o contrato em código; o hook transforma o código em regra.

SLI, SLO, SLA e orçamento de erro

  • SLI (indicador): uma medida, por ex. "% de horas com silver publicada até às :20".
  • SLO (objetivo): o valor que te comprometes a cumprir, por ex. "99 % por mês".
  • SLA: o compromisso com consequências para um cliente. Raramente se aplica a um projeto pessoal.
  • Orçamento de erro: 1 % de 720 horas = ~7 horas por mês que podem falhar. Gasto o orçamento, param-se as mudanças arriscadas.

  • Plataforma (métodos USE e RED): utilização, saturação e erros dos recursos; taxa, erros e duração dos pedidos. É o Prometheus/Grafana.
  • Dados: frescura, volume, esquema, distribuição, linhagem. É o G2, o alarme de frescura e, a seguir, o histórico no OpenMetadata.
  • Dead man's switch: alarmes que disparam quando um sinal esperado não chega (backup, cópia do lake, silver). Apanham também o que nem chegou a correr.
  • Fadiga de alertas: cada alerta tem de pedir uma ação. Um alerta que se ignora é pior do que nenhum.

Orquestração e governança a fundo

Objetivo: perceber os padrões de orquestração e de governança que separam um júnior de um sénior.

Orquestração

  • Tarefas idempotentes e atómicas: cada tarefa ou faz tudo ou não faz nada visível (aqui, o merge é o momento atómico).
  • Retries com cabeça: repetir erros transitórios (rede), não repetir erros determinísticos (o G2 usa AirflowFailException).
  • Agendamento por intervalo de dados: a corrida das 10:10 trata a hora 09 (a hora fechada), não "agora".
  • Agendamento por dados (assets/datasets no Airflow 3): uma DAG corre quando outra produz um dado, em vez de a uma hora fixa. É o caminho natural para o gold.
  • Executores: KubernetesExecutor (um pod por tarefa, isolamento e imagens por projeto) vs Celery (workers sempre ligados, menos latência).
  • Ferramentas vizinhas: dbt (transformações SQL testadas e documentadas), Dagster (orientado a assets). Saber quando cada uma ajuda conta numa entrevista.

Governança

  • Catálogo: onde estão os dados, o que significam, quem é dono (OpenMetadata).
  • Linhagem: de onde vem cada coluna (OPC UA → bronze → silver → gold). O padrão aberto é o OpenLineage, que o Airflow emite.
  • Glossário: os termos do negócio (OEE, paragem, ativo) ligados às colunas.
  • Dados pessoais e RGPD: identificar, minimizar, mascarar, apagar a pedido. Aqui não há dados pessoais, mas numa empresa é o primeiro tema da governança.
  • Retenção: quanto tempo se guarda cada camada e porquê (branches com 7/30 dias, dumps com 14 dias).

Quota (OCI)Regra da conta que limita quanto de um serviço se pode criar; a zero, nada desse serviço se cria. O que já existe continua.
WALWrite-Ahead Log: o registo onde o Postgres escreve cada alteração antes de a aplicar, para recuperar de uma falha.
Página completa (full-page image)Cópia inteira de uma página de 8 KB que o Postgres põe no WAL na primeira alteração depois de cada checkpoint.
Multipart (envio em partes)Envio de um ficheiro grande em vários pedaços. Na Oracle exige OBJECT_OVERWRITE, que a VM não tem; por isso os backups vão sempre num só pedido.
Range (lakeFS)Pedaço do índice de um commit: uma lista ordenada de ficheiros. Os commits partilham os ranges que não mudaram.
Ciclo de vida (lifecycle) de um bucketRegra do Object Storage que apaga ou arquiva objetos sozinha, sem pedidos pagos.
App-of-appsUma aplicação do Argo CD cujo conteúdo são outras aplicações.
ApplicationSetGerador de aplicações do Argo CD a partir de um padrão (pastas, listas).
ClusterSecretStoreConfiguração do ESO: onde está o cofre e como se autenticar.
DAG bundleOrigem dos ficheiros de DAG no Airflow 3 (pasta local ou repositório git).
DERPRelay do Tailscale usado quando não há ligação direta.
ESOExternal Secrets Operator: cria Secrets do Kubernetes a partir de um cofre externo.
ExternalSecretPedido ao ESO: "cria este Secret a partir deste segredo do cofre".
GHCRGitHub Container Registry: o registo de imagens do GitHub.
IdempotenteCorrer uma vez ou dez dá o mesmo resultado.
Import (Terraform)Passar um recurso que já existe para a gestão do Terraform, sem o recriar.
Instance principalAutenticação da Oracle em que a própria VM prova a sua identidade, sem chave.
KillMode=processConfiguração do systemd que, ao parar o k3s, não termina os contentores com calma.
pod_overrideAlteração ao pod de uma tarefa do Airflow (aqui, a imagem).
Prune / selfHealArgo CD: apagar o que saiu do git / repor o que foi mudado à mão.
Segredo zeroA credencial que permite ler o cofre e que, por isso, não pode vir dele.
Security listFirewall de uma subnet na Oracle.
tfstateFicheiro onde o Terraform guarda o que gere; contém dados sensíveis.
NetworkPolicyRegra de que tráfego um pod pode receber (ingress) ou enviar (egress).
Pod Security StandardsNíveis privileged / baseline / restricted que o Kubernetes impõe por namespace.
ValidatingAdmissionPolicyRegra (em CEL) que o próprio Kubernetes avalia antes de aceitar um objeto.

RPO / RTOQuanto se pode perder / quanto tempo se pode estar parado, numa recuperação.
SLI / SLO / SLAIndicador medido / objetivo assumido / compromisso com consequências.

MedalhãoCamadas bronze (bruto), silver (limpo), gold (negócio).
